## 1. The digest switch (plan 7.2)

`resolveFieldContent` takes a required `policy`:

| item | `raw` (default) | `digest` |
|---|---|---|
| chaptered, under the direct-pass ceiling | raw transcript, no declaration | **chapter digest**, declared ("field input policy "digest": … in place of the N-char transcript …") |
| chaptered, over the ceiling | chapter digest, declared (unchanged) | chapter digest, declared |
| chapterless, under the ceiling | raw transcript | raw transcript, declared ("has no chapter list, so its content fields read the raw transcript") |
| chapterless, over the ceiling | **fails naming both facts** (unchanged) | fails naming both facts |

Under `digest` the item's `contentMode` is `chapter-digest`, so every field that reads `ctx.content`
(titles already read chapters by choice since 2026-08-24; description, thumbnail text, pinned
comment and the written tags) reads `renderChapterDigest`. Tag assembly and the pools still test
against the item's content text, unchanged.

The policy is resolved once per run (`resolveFieldInputPolicy`): absent = `raw`, **said** in the
log ("the declared default; … states none"); a non-default policy's line also goes into the run's
warnings; an unknown value fails the job by name. It is the store key `fieldInput` (read at job
time, no store default, like `chapterEngine`) and the CLI's `--field-input`. There is **no Settings
control** (#214). **The default did not move**: plan 7.4 moves it only on Owen's verdict.

Each saved item carries `_field_input: {policy, mode, content_chars, transcript_chars}`.

## 2. Every call asks for its own step (#209)

Before P4 every field unit on a model shared ONE window per item: the 4096-bucket of the largest
field prompt that model would send (sized on the pending prompt plus a 2,000-char allowance) plus
its 8,192 budget and 512, raised to the largest window the JOB had already asked that model for
(the ratchet), so after snap's thinking titles loaded the 27B at 24,576 every later field call
asked 24,576. The whole-transcript engine pinned one window per run with the Settings
`chapterNumCtx` 16,384 as a floor. The one-call sites bucketed to 4096 on their own prompt.

Now each call asks `loadContextFor(its prompt, its budget)`. Reloads stay bounded by the lease, not
by a floor: within a job a call that needs more grows the load once, one that needs less runs on
the window already loaded (lease.ts, unchanged). Nothing carries a floor from another stage or job.

| call site | before | after |
|---|---|---|
| field calls (`LocalFieldUnit`: titles, thumbnail text, pinned comment, tags) | one window per model per item: bucket4096(largest field need + 8,192 + 512), ≥ the job's largest earlier window on the model; e.g. Duffy raw 24,576 (floor from the thinking titles), milo raw 40,960 | own step, budget 2,048: Duffy raw titles 8,192 / thumbnail 16,384; milo raw titles 16,384 / thumbnail 32,768; **digest: 8,192 (Duffy, f2) and 16,384 (60+ min)** |
| description (`DescriptionUnit`, 3 calls) | the same shared window | own step, budget 4,096: Duffy raw 16,384, milo raw 32,768; digest 8,192 / 16,384 |
| scrub, Soften (`askToRewrite`, thinking on) | bucket4096(prompt + 8,192 + 512) ≈ 12,288 for a ~900-token prompt | budget 16,384, step 24,576 (like a thinking title) |
| more titles (operator replay) | bucket4096(prompt + 8,192 + 512) | own step, budget 2,048 |
| re-roll revise (thinking on) | bucket4096(prompt + 8,192 + 512) | own step, budget 8,192 (kept) |
| re-roll decide (the 9B scorer) | **none stated** (the server's default load) | own step, state + 1,024 |
| insights distiller | bucket4096(prompt + 2,048 + 512), max 32,768 | own step: ~2.1k-token prompt → 8,192 |
| compilation summarizer | bucket4096(prompt + 4,096 + 512), max 40,960 | own step: a 60,000-char chunk → 24,576 |
| compilation package (JSON) | bucket4096(prompt + 4,096 + 512), max 40,960 | own step |
| whole-transcript chapters (stage 1 samples, name scaffold, details) | ONE window per run: bucket4096(largest stage-1 window + 8,192 + 512), floored at `chapterNumCtx` 16,384 and the job's ratchet | each call its own step (budget 8,192): a 2,800-word window → 16,384; the GPU-ceiling warning kept, from the largest stage-1 call |
| snap outline / decide / titles (P8b) | own step already (`loadContextFor` in snap-chapters.ts) | unchanged; the helper moved to context-check.ts |

Measured examples above are from the offline table in section 5. `check:p4` holds the helper's
boundaries (exactly one step; one token over; the margin; a grid of 200 prompt sizes × 6 budgets
never fails `checkBeforeSending` on the window it asked for, and is never one step too big), and
each site's budget and step on a 12,000-char prompt; `test-crucible-p4.js` holds what the
description, a rewrite pass and the summarizer actually send the fake and that a job grows once.

**A fact for the reader, not a decision.** On the Mac (mlx-darwin) the load context is admission
only: the 27B and 9B manifests say mlx-lm "is handed no context and allocates KV on demand", so a
smaller step changes no memory or speed there. On the PC (cuda-linux vLLM) it sizes the KV pool.

## 6. The check before sending

Every local chat goes `transport.chat` → `job.hold` → `checkContext` → `checkBeforeSending`
(nothing else in `electron/` posts to `/v1/openai/chat/completions`: grep), and every decide
`transport.decide` → `checkBeforeSending` with the state. The refusal (`over_context`) names the
call (`what`), the estimate (need, and the prompt's share), the budget and the loaded context with
its source (max_model_len / load context / context ceiling); `check:p4` asserts each part. The
door's earlier check against the call's own sized load now names the prompt estimate and the
budget as well (it named only the need before).

## 7. `GET /v1/capability?context_tokens=` — built

The vendored SDK 1.0.34 has `client.capability(options, {class, contextTokens, concurrency})`
(`CapabilitySizing`). `lease.ts` asks it before every `load-model` that states a context, with
`class=generate`, the load's context and `concurrency=1`:

- the server's `400 context_over_limit` → `over_context` carrying the server's sentence ("… cannot
  serve <model> at the N tokens <job> needs, one request in flight: <server's words>. Nothing was
  loaded and nothing was evicted.");
- a `generate` ceiling row for the model below the size → the same, naming the ceiling and its
  `bound_by`;
- a model with no ceiling row → proceeds and says the load is the judge;
- a pre-1.0.24 server (act `analysis`) → not asked, said in the log.

**Deviations from the plan's wording (7.2 "After 1.0.24"), stated:** (a) it is asked at the load,
not at queue admission: at admission no prompt exists (transcription and chapters come first), so
"the run's real max context" would be a guess; the load is the first moment it is a fact and is
still before the card is reserved or anything evicted. (b) A no-fit **fails**, it does not park or
move: the ceiling is the host's memory at one request, which waiting does not change, and nothing
moves to another server on its own (#205). Held by `test-crucible-p4.js` (4 cases, the query string
exact and before the load). Not verified against a live 1.0.40.

## 8. Owen's decisions (open; nothing changed)

1. **Identical description candidates.** Facts: the description unit asks the 27B for 3 candidates
   from one prompt with no temperature (LEDGER #125: provider defaults); the 27B manifest states no
   sampling ("a manifest says what a model needs, not how to sample it"); mlx-lm's server decodes
   at its own `--temp` default, 0.0 (mlx_lm/server.py in Crucible's llm env), so the three answers
   are the same text. Recorded: the three candidates of each Crucible-era run are 734/734/734 and
   837/837/837 chars at 145/147 tokens, and the two alternate-description scrubs 840/840 chars at
   4,807/4,807 tokens. The two
   options on the table: **(A)** send a temperature on local candidate draws (a sampling parameter
   on the local path only; #194 forbids it only for cloud), so the three differ; **(B)** ask for
   one candidate on a deterministic local model and stop spending two calls on copies. Not decided
   here.
2. **The digest default** (plan 7.4): `raw` stays the default until Owen's blind A/B verdict.
   `--field-input digest` on the CLI and `fieldInput: "digest"` in the store are the B arm.
3. **Shrinking a resident model across jobs** (#209's second sentence: "A model resident at a
   larger context than the next job needs is reloaded at the smaller one"). NOT built: lease.ts
   still takes a resident model at its larger window. Fact for the decision: on the Mac the load
   context is admission only (mlx allocates KV on demand), so a shrink-reload there costs a 17 GB
   reload and buys nothing; on the PC it would free KV. Build it PC-only, or both, or leave it?
4. **The description budget** stays 4,096 on one outlier (a 6,066-char run-on in August). If Owen
   reads that as a malfunction rather than an answer, 2,048 would be supported by everything else.
