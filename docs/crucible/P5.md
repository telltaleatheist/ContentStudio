# P5: every transcription is Crucible's `asr` job on `qwen3-asr-1.7b`

LEDGER #206 (Owen, 2026-09-25): "no more local whisper. we're going with crucible for
transcription too, and we'll be using qwen asr ... probably the big model, 1.7b, since we want
accuracy. we should make sure to pass in any useful metadata with the prompt, too, in case it
might have proper nouns spelled out correctly and it can act as a seed for proper nouns."
This page covers the pipeline and the editor, as that ruling does. It records what was built,
what P1 has to provide, and every acceptance number measured on the Mac.

## 1. What changed

| Piece | File | What it does |
|---|---|---|
| The job | `electron/crucible/asr.ts` | One asr job: check `/v1/info`, upload, submit, follow events, fetch `transcript.json`, and DELETE on cancel. Ported from Briefcase's `crucible-asr-job.ts` and `asr-models.ts`. |
| The context | `electron/services/transcription/asr-context.ts` + `shared/pipeline/transcription.yml` | The verbatim instruction (#203) and the item's spelling facts (#206). The token estimate is conservative, control tokens are scrubbed, and the least specific field is cut first. |
| The facts | `electron/services/transcription/asr-facts.ts` | Reads the facts from disk: the filename title, the job name, the channel's brand terms and promoted items, and an earlier run's titles, tags and description (by source key). | The transcript | `electron/services/transcription/crucible-transcript.ts` | Turns `transcript.json` into sentence captions at the aligner's word times (Briefcase's `alignWordsToText`) and into punctuated word tokens for the editor. |
| The door | `electron/services/transcription/crucible-transcription.ts` | The venue seam (P1 wires it), one job per server in this process, progress bands, and the model name `crucible:<server>:qwen3-asr-1.7b`. |
| Pipeline | `electron/services/metadata/whisper.service.ts` (name kept for its callers) | Extracts FLAC (plus the WAV when tagging), builds the context, runs the job, builds captions and words, and runs speaker tagging per caption. |
| Editor | `editor-backend/cli/transcribe.py`, `electron/services/editor/editor-asr.ts`, `python-service.ts`, `editor-ipc.ts` | Python keeps the audio logic. Each decode is an `asr_request` that main answers over stdin (plan §8.2). |

| Acceptance | `tools/asr-acceptance.js`, `tools/asr-word-timing.py` (§8.3 numbers), `tools/crucible-raw-client.js` | The live runs in §4. The raw-fetch client is for these tools only. |

### The request, exactly

```
POST /v1/jobs {type:'asr', model:'qwen3-asr-1.7b',
               params:{language:'en', vad_filter:false, word_timestamps:true, context:<string>},
               inputs:{<safe name>.flac:{blob_id}}, client_ref:'contentstudio:<pipeline|editor>:<id>:<rand>'}
```

`context` is never blank. When nothing is known about the item it is the instruction alone.
Before anything is uploaded, the `asr` and `align` rows of `/v1/info` are read. A server without
`qwen3-asr-1.7b` or `qwen3-aligner` installed (or without the `align` job type) is refused by
that name. Nothing falls back to whisper (Law 1).

### How a transcription ends

`CrucibleAsrError.kind` tells the outcomes apart; code branches on the kind, never on the message
(Law 10).

- **failed**: the item fails with the server's own code and message, whole. `asr_decode_loop`
  and its time range reach the queue row, or the editor's error, verbatim.
- **cancelled**: the job was DELETEd on the server, never abandoned. The pipeline's
  `WhisperService.cancel` and the editor's `killProcess` both abort it.
- **busy**: the lane is held by another client. The item fails with the holder's line. P3 turns
  this into parking; until then there is no parking.
- **unavailable**: not connected, unreachable, the model or aligner is missing, the token was
  refused, or the stream was lost past its budget.
- **refused**: the server refused the request itself (a param, the context).

### Declared behaviours (Law 8)

- **One job per server, in this process.** The pipeline runs up to 5 transcriptions at once and
  the editor adds one. Jobs for one server queue in arrival order in
  `crucible-transcription.ts`, and each wait is logged with the number of jobs ahead. P3's lanes
  replace this.
- **A Qwen piece whose text does not line up with its words** gets captions cut from the
  words' own unpunctuated text (Briefcase's rule). The count is logged per item. It was 0 in
  every acceptance run.
- **A report that cannot be read** while looking for earlier titles is skipped. A warning names
  the file.

### Left for P10 (unreachable now, not deleted)

`whisper-bridge.ts` and its exports, the whisper catalog entries (`electron/components/catalog.ts`
and the editor's `asset-catalog.ts`) and `binary-resolver.getWhisperCliPath/getWhisperModelPath`
stay in place, and no code path reaches them. The **`whisperModel` setting** is also unused
now. It is still read by `setSelectedWhisperModel`, the Settings dropdown, the
components:uninstall guard and the setup dialog's "choose a Whisper model" list; P10 removes it.
Startup readiness no longer requires `whisper-engine` or a whisper model. It no longer
auto-downloads them, and a missing model no longer opens the setup dialog. The saved-transcript
key `whisper_model` keeps its name, so old records stay readable. It now holds
`crucible:<server>:qwen3-asr-1.7b`.

## 2. What P1's client must provide (the one-line swap)

The whole app reaches Crucible for transcription through one seam:

```ts
import { setAsrVenueResolver } from './services/transcription/crucible-transcription';
setAsrVenueResolver(() => ({ server: <registry name>, client: <the SDK CrucibleClient for it> }));
```

Until that line runs, every transcription fails with `crucible_not_connected` ("Transcription
runs on Crucible (LEDGER #206), and no Crucible server is connected to ContentStudio. Connect one
in Settings › Crucible Servers."). The resolver is called on every transcription, so a Settings
switch of server applies from the next item. It must throw a named error when no server is
selected; asr.ts passes that error through.

`client` must satisfy `AsrCrucibleClient` (asr.ts). It is a structural subset of the vendored
SDK's `CrucibleClient`, so **the SDK client passes as it is**:

| Call | SDK signature used | Fields read |
|---|---|---|
| `info()` | `info(options?)` | `server.version`, `host.backend`, `jobTypes`, `capabilities[].jobType`, `capabilities[].models[].id/.installed` |
| `upload(blob, {filename})` | same | `blobId` |
| `submit(request)` | `submit(JobRequest)` with `{type, model, params, inputs:{name:{blobId}}, clientRef}` | the job id |
| `events(jobId, {lastEventId})` | async iterable of `JobEvent` | `id`, `event`; `progress.data.{fraction,message,extra.stage/processed_s/total_s}`; `failed.data.error.{code,message}` |
| `artifact(jobId, 'transcript.json')` | same | bytes |
| `cancel(jobId)` | same | `status` |
| `job(jobId)` | same | `clientRef` (to adopt a submit whose answer was lost) |
| `activity()` | same | `running[]/queued[].{jobId,type}` |

Errors are read **structurally**, by the SDK's own names and fields. No `instanceof` is used, so
P5 does not import the SDK:

- `name === 'CrucibleUnreachable'`: weather. The upload and submit are retried and the stream is
  reopened.
- `CrucibleBusy` / `CrucibleLeased`: the `busy` kind. Their `busyLine` / `leasedLine` and
  `jobId` are used.
- `CrucibleAuthError`, `CrucibleVersionError`, `CrucibleNotACrucible` and
  `CrucibleProtocolError`: the `unavailable` kind.
- Anything else with `code` / `serverMessage`: `refused`, except that `env_missing`,
  `model_not_installed`, `unknown_model` and `job_type_disabled` are `unavailable`.

Also for P1 and P3 to wire:

- **The ledger.** `runAsrJob` takes an optional `ledger: {record(jobId), settle(jobId)}` for P3's
  in-flight ledger. The door does not pass one yet.
- **The metadata CLI** (`scripts/generate-metadata-cli.js`) sets its venue from
  `tools/crucible-raw-client.js pairedVenue()`. P1 replaces that one line with the registry's
  client. The acceptance tools do the same.
- **Readiness.** When P1's readiness service exists, it should disable transcribe controls with
  its one reason. Today a transcription simply fails with `crucible_not_connected`.

## 3. The context, as sent

The instruction (`shared/pipeline/transcription.yml`), then one line per known fact, most
specific first:

```
Verbatim transcript. Transcribe every disfluency exactly as spoken, including filler sounds: um, uh, ah, er, hmm, and false starts and repeated words. What is known about this recording is below: use it only for the spelling of names, places and terms, and write only what is actually said.
Title: hank kunneman
Job: 3 - hank kunneman.mov
Also titled: hank kunneman says god told him gas prices would go down down down / … (the earlier run's 10 titles)
Names: owen morgan, telltale, telltale atheist
Names and topics: sermon, Glory of God, Donald Trump, Jesus, Hank Cunhamon, Venezuela, … (the earlier run's tags)
Also mentioned: the book "God's People: Christian Nationalism in the Third Reich"; … (the channel's promoted items)
Description: Hank Kunneman's gas price prophecy arrives with … Kunneman's Venezuela…   (cut to fit)
```

That one is 2,094 characters and an estimated 699 of the 700-token budget. The server counts
the real tokens against its limit of 1,024, and every job was accepted. The editor's context for
the 2026-09-23 session is the session name, its five story titles and the active channel's terms:
803 characters, an estimated 268 tokens.

The proper nouns in this window (AI, AOL, Claude, Opus, Qwen, Dallas, Texas, United States,

so the seed has nothing to correct here, and it changed none of them. Qwen spells "Qwen" where

**On 19 against 11 and 9.** Owen's direct `qwen_asr` run got 19. Crucible's first run got 11, and
these three runs got 9, 9 and 11. The cause is the **cut points**, not the context length:

1. The two filler-prompt contexts (166 and 290 characters) gave identical fillers. The
   803-character context gave two more.
2. The server's own measurement agrees (crucible `asr/qwen3-asr-1.7b.toml`, mlx-darwin block).
   On this same window with the filler prompt, the package's own splitter gave 13 and the
   worker's splitter gave 11, on the same engine and weights. The same engine on the same cuts
   moved between 19 and 13 across runs, because "a sample rounded differently tips a borderline
   um". One uncut 600 s decode found zero.
3. Crucible cuts at quiet points into pieces of at most 180 s (4 here). Qwen's package cuts
   differently, and extracts its own samples from the file.

Over a longer stretch the gap to whisper.cpp is clear. On the first hour of both tracks in (b), Crucible wrote 53 fillers where whisper.cpp wrote 29. Fillers are fragile at the margin. The count moves by a few with cut points and sample rounding,
not with the seed. Whether 9–11 is enough to cut on is Owen's call (§6).

### (b) Word timing against whisper.cpp (plan §8.3)

The run: `tools/asr-acceptance.js editor` ran transcribe.py over a copy of
`2026-09-23_compounds.zip` with `--max-seconds 3600` (the first hour of each track), on the new
asr_request protocol. The session's own sidecar was not touched. The comparison is its
whisper.cpp (`large-v3-turbo`, `-ml 1 -mc 0`) sidecar, restricted to the same first hour. Both
sidecars came out of the same extraction, VAD compaction and `map_words`. Words are matched per
track by difflib on their letters, and the differences are measured in file seconds.
frameSeconds = 0.03337 (29.97 fps).

| | t0 mic | t1 screen | both |

| matched | 3,738 | 3,242 | 6,980 |
| agreement (of whisper's / of Crucible's) | 96.7% / 85.3% | 94.9% / 91.4% | |
| fillers (whisper / Crucible) | 12 / 29 | 17 / 24 | 29 / 53 |
| \|Δstart\| median / p90 / p99 | 0.300 / 0.983 / 10.67 s | 0.294 / 1.008 / 4.48 s | 0.297 / 1.000 / 8.50 s |
| \|Δend\| median / p90 / p99 | 0.220 / 0.880 / 10.04 s | 0.244 / 0.936 / 3.50 s | 0.230 / 0.900 / 8.35 s |
| signed Δstart / Δend median (Crucible − whisper) | +0.230 / +0.140 s | +0.218 / +0.148 s | |
| share off by more than 1 frame (start / end) | 91.6% / 89.3% | 91.5% / 90.3% | 91.5% / 89.8% |
| loops: server re-decodes / loop regions transcribe.py asked for / repetition runs surviving | 0 / 0 / 0 | 0 / 0 / 0 | whisper.cpp survivors: 0 / 0 |
| audio sent (compact WAV) / job time | 1,985 s / 424.3 s | 1,396 s / 401.7 s | wall 837.7 s for the run |

**By the §8.3 rule this FAILS**, and by a wide margin. The rule wants p90 \|Δ\| within one frame
(0.033 s) and a median under half a frame. What was measured is a median of 0.3 s, a p90 of
1.0 s, and a systematic bias: Crucible's words start about 0.22 s later than whisper.cpp's.

**But the rule measures disagreement with whisper.cpp, and whisper.cpp is not the truth.** I
checked both against the audio itself. For each matched word that follows at least 0.6 s of
silence in both transcripts, I found where the track's energy rises (10 ms RMS bins, the first
bin above 10% of the word's loudness, going back from its peak):

| | words after a pause | \|start − energy onset\| median | signed median | Crucible closer |
|---|---|---|---|---|
| t0 mic | 48 | whisper 0.455 s, **Crucible 0.110 s** | whisper −0.455 s (early), Crucible −0.045 s | 37 of 48 |
| t1 screen | 10 | whisper 0.550 s, **Crucible 0.194 s** | whisper −0.495 s, Crucible −0.055 s | 7 of 10 |

whisper.cpp's `-ml 1` word starts are about half a second early at pause onsets. Qwen's aligner
lands within about 50–100 ms. So the 0.22 s bias is mostly whisper.cpp's error, not Qwen's. This
referee is crude: 58 words, an energy threshold, and pauses only. Its direction agrees with
#203, where ten ums cut at the aligner's spans were "flawless". The p99 of 4–10 s comes from
difflib pairing a repeated word across a stretch where one transcript has words the other lacks.
It is not a timing error. The rule as written cannot pass against a reference that is itself
0.4–0.5 s off. Owen decides (§6). The editor is switched per #206.

## 5. Checks (`npm run check:asr`, 37 checks, all pass)

- **transcript.json to captions:** whisper.cpp's SRT fields, empties, overlaps (duplicate
  dropped, run-on trimmed, jitter, clamp), past 10 h and past 99 h, and the strict reader.
- **Briefcase's punctuation cases:** contractions, hyphens, dash, a word the text lacks, CJK, and
  the counted alternate. A 180 s piece becomes three sentence captions, fillers stay in, and
  "don't" becomes one token.
- **The params** are exactly the four keys, and a blank context is refused.
- **The context:** the shipped template, the order, the instruction-only case, the scrub, the
  cut order (description, then notes, then promoted items), CJK, the filename rule, and an
  earlier report found by source key.
- **Progress:** stage frames and consecutive bands.
- **The job, against a scripted server:** the exact submit, cancel sending a DELETE, a failed job
  carrying the server's message with the `asr_decode_loop` range, a missing model or aligner
  refused before upload, busy, a lost submit adopted by `client_ref`, "not connected", and one
  job per server.
- **The editor protocol**, with transcribe.py running for real: the loop-region round trip
  (region sent, words shifted by its start), a failed job arriving whole as transcribe.py's
  error, and the words reader (probability null means no `prob`, and a missing start is refused).

`npm run build:all` and `npm run check:pure` stay green.

## 6. Open questions for Owen

1. **Fillers.** Crucible's cuts give 9–11 fillers on the reference window, against the 19 you got
   through `qwen_asr` directly. The server's manifest shows the same engine moving 11–19 with cut
   points and sample rounding. Is that enough to cut on? If not, Crucible would need a
   ContentStudio-side choice of piece length, which is a server change.
2. **The seed's side effects** on the hank video. With the context, "ICE Gestapo" became "ICE
   stopper", "religious graft" became "craft", and "going to" became "gonna" three times. Which
   did you actually say? If the context pushes the model away from verbatim words, the
   description (the longest field) could be dropped from the context and the names kept.
3. **Speaker tagging on sentence captions** needs a re-run with your real enrollment recording.
   Short host lines ("Check this out.") score near the CLIP line. Should very short captions be
   scored together with their neighbours?
4. **Editor word timing.** Plan §8.3 kept whisper.cpp as the editor engine until you accept the
   measurement. #206 says "no more local whisper ... that covers the editor", so this build has
   already switched the editor to Crucible. By the letter of §8.3 the result fails: median 0.30 s
   and p90 1.0 s against whisper.cpp. Measured against the audio's own onsets, whisper.cpp is the
   one that is about 0.45 s early and Qwen is within about 0.1 s. Do you accept Qwen's timings on
   that basis, perhaps after listening to a few cuts? Or do you want the rule restated against an
   audio reference?
